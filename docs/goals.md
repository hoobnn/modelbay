# 目标与范围

为什么这么分层见 [0001](decisions/0001-single-implementation-architecture.md)。本文写要做到什么、不做什么，以及现在做到了哪一步。

## 要解决的问题

火山方舟、豆包语音、阿里云百炼、MiniMax、OpenAI 这几家上游经常改参数、上下线模型。生图、生视频、语音、复刻、异步任务和素材上传，各家接口差异很大，没有现成的开源统一实现。Modelbay 用一份 TypeScript 实现覆盖这些平台，SDK、MCP、CLI 都从同一份模型声明派生。

## 目标

| 编号 | 目标               | 怎么判断达成                                                                                                      |
| ---- | ------------------ | ----------------------------------------------------------------------------------------------------------------- |
| G1   | 一处修改，处处生效 | 上游改一个参数范围、默认值或模型状态，只改一个声明文件。SDK 的校验、MCP 的工具 schema、CLI 的模型清单都从声明派生 |
| G2   | 好扩展             | 加模型只加一个声明文件；加平台只动它自己的包和注册表；加 MCP 工具只改平台自己的工具定义                           |
| G3   | 接入容易           | 外部 TypeScript 项目只装 `modelbay` 并配好 key，十行以内调通生图、生视频、配音中的任意一种，异步轮询由 SDK 处理   |
| G4   | 核心不绑定运行时   | `@modelbay/core` 和各平台包的根入口能在 Node、Bun、Deno 和浏览器里加载。Node 专属能力只在 `/node` 子路径          |
| G5   | 上游变化能被发现   | 定时任务现抓官方文档，和声明双向核对：下线、列表缺失、新模型都能定位到具体声明，并生成改动草稿                    |

## 不做的事

- **HTTP 网关和托管服务。** 等第一个非 TypeScript 消费方出现再说。
- **画布、工作流编排。** 节点、端口、插件清单、审批由上层应用负责。
- **不自动合并声明改动。** 对账工具会生成生命周期补丁和新模型骨架，但都附官方原文引用、走草稿 PR，由人核对原文后合并。
- **不做其他语言的 SDK。**
- **不管计费、配额和密钥。** SDK 只上报用量，key 由宿主传入，SDK 不存储。
- **不负责结果的下载和入库。** 结果只返回 URL 或字节。

## 现状

已完成：

- `@modelbay/core`：能力、声明格式与校验、默认模型选择、异步任务运行、平台描述类型。
- 五个平台包（方舟按量与套餐、百炼、MiniMax、豆包语音、OpenAI 与 OpenAI 兼容渠道），共 85 个模型声明。
- `modelbay` 汇总入口与平台注册表，`modelbay/node` 注入 Node 专属能力。
- `@modelbay/mcp`：`modelbay-mcp <平台>`，支持方舟、MiniMax、百炼、豆包语音，工具从声明生成，本地 stdio 冒烟通过。
- `@modelbay/cli`：`modelbay models / capabilities / doctor / generate`。
- 上游文档对账：每天现抓官方 Markdown（个别站点浏览器渲染），统一抽取模型清单和下线信息，与声明双向核对，差距进跟踪 issue，生命周期补丁开草稿 PR。

接下来：

- **首次发布 0.x。** 需要维护者批准，见 [工程规范](engineering.md#版本与发布)。
- **在 MCP 客户端里实跑。** 目前用本地 stdio 冒烟代替。
- **夜间真实冒烟。** 每家用最便宜的一档跑一次真实调用；key 放在哪、预算多少还没定。
